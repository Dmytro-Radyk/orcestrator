# Інтерфейс і API

Статус: специфікація цільового UI та API v1. У `apps/web/` є локальний клікабельний прототип основних екранів на демонстраційних даних; API v1, авторизація та реальне виконання ще не підключені. Повна специфікація нижче лишається цільовою. [Навігація](README.md).

Уточнення майстра: «Допомогти продумати ідею» або «Проєкт уже придуманий» → необов'язкова концепція → детальний план → AI-рекомендації профілів/моделей на кожну задачу → прийняття. Ручне призначення — коригування рекомендації. У локальному UI додано окремий endpoint реального планувальника з конфігурацією на сервері; його поточні можливості й обмеження описані в [AI-PLANNING.md](../AI-PLANNING.md).

## 1. Навігація продукту

```text
Робочий простір
├─ Огляд                     # Активні запуски, запити на рішення, ресурси
├─ Проєкти
│  └─ Проєкт
│     ├─ Мета й контекст
│     ├─ Команда
│     ├─ План
│     ├─ Запуски
│     ├─ Артефакти та зміни
│     ├─ Пам'ять
│     └─ Налаштування
├─ Агенти                    # Профілі, версії, навички, eval
├─ Моделі та підключення      # API, локальні моделі, CLI, health
├─ Шаблони                   # Команди й типові процеси
├─ Погодження                # Конкретні дії, причини, scope і строк дії
└─ Налаштування системи      # Workers, roots, секрети, ліміти, backup
```

## 2. Створення проєкту

| Крок | Дані користувача | Вихід системи |
| --- | --- | --- |
| Мета | Новий/існуючий проєкт, тип роботи, бажаний результат | Draft цілі та критеріїв приймання |
| Джерела | Репозиторій, папка, документи, матеріали | Manifest доступних джерел, перевірка доступу |
| Команда | Автопідбір / вручну / змішано, дозволені провайдери | Рольові слоти, кандидати, пояснення, доступність |
| План | Автоплан або шаблон, редагування задач | Валідний граф, expected outputs, gates |
| Ресурси та права | Бюджет, паралельність, інструменти, делегування, автономність | Preflight, точність оцінки, блокери |
| Перегляд | Перевірка складу команди та плану | Зберегти проєкт / зберегти й запустити |

Підбір команди до деталізації плану є попереднім. Після редагування плану система переоцінює слоти, а ручні фіксації зберігає, якщо вони лишилися допустимими. Автопланування саме потребує модельного запиту, тому його оцінка ресурсу і режим запуску видимі до виклику; ручний план не потребує моделі.

Перед автоплануванням майстер зберігає draft-ревізію і створює допоміжний planning Run з обмеженим бюджетом. Отриманий PlanProposal можна редагувати або відхилити. Початок робіт над проєктом — окрема команда створення execution Run з прийнятою пропозицією.

У картці агента: роль, модель/backend, потрібні можливості, права, контекст, оцінена ціна/час з рівнем впевненості, результат останнього health check. «Рекомендовано» має коротке пояснення. Невідомі ціни або можливості позначаються явно.

## 3. Редагування проєкту

Збереження створює ревізію. UI показує порівняння мети, команди, плану, прав і ресурсів. Вибір: використати ревізію для наступного запуску або окремо запропонувати зміну активного плану.

Для зміни активного плану UI показує affected tasks: продовжаться; будуть зупинені; потребують повторного виконання; втратять актуальність результату чи дозволу. Команда застосовується з expected revision. Конфлікт редагувань повертає diff актуальної версії; останній запис не перемагає мовчки.

## 4. Екран запуску

Основна область перемикається між графом задач, канбаном і timeline. Бічна панель показує вибрану задачу/агента: інструкції, входи, поточний invocation, виходи, права, usage та журнал. Дерево субагентів — окремий режим: не змішується з ребрами залежностей графа.

Дії Run: pause, resume, cancel, fork from snapshot, export report. Дії Task: переглянути призначення, поставити в чергу повідомлення, змінити наступну спробу, retry, cancel subtree, відкрити diff/artifacts. Доступні дії залежать від стану й capabilities backend.

Стани «команда зупинки надіслана», «процес завершено» і «потрібна звірка» мають різні позначки. Від'єднання вкладки не скасовує роботу. Події після reconnect дочитуються з cursor; UI не створює повторний запуск через втрату відповіді HTTP.

Кілька кандидатів показуються поруч із джерелом, часом, usage та оцінками. Прийняття кандидата або synthesis посилається на конкретний artifact hash. Для коду окремо показуються diff окремого виконавця і фінальний інтегрований diff.

## 5. Режими автономності

| Режим | Поведінка |
| --- | --- |
| Керований | План, команда й визначені дії проходять ручне прийняття |
| Збалансований | Затверджений план виконується автоматично; рішення поза його межами повертаються користувачу |
| Автономний у межах правил | Планування й делегування автоматичні в межах виданих прав і бюджетів |

Режим автономності не відключає sandbox, бюджет чи заборону доступу. Користувач може змінювати правила погодження, але model output не може. Екран рішення показує конкретну дію, причину, наслідок, джерело policy та можливість відхилити. Технічні подробиці worker/SQL приховані від звичайного сценарію створення проєкту.

## 6. Публічний API v1

REST для запитів і команд; SSE для подій. Ідентифікатори opaque. Схеми OpenAPI та клієнт генеруються з `packages/contracts`. Для довгих операцій відповідь `202` з `operationId`; її стан читається окремо. Мутації приймають `Idempotency-Key`; зміни існуючої сутності додатково вимагають `If-Match` або `expectedVersion`.

| Маршрут | Семантика |
| --- | --- |
| `GET/POST /v1/projects` | Список/створення, cursor pagination |
| `GET /v1/projects/:id` | Поточна версія і metadata |
| `POST /v1/projects/:id/revisions` | Нова ревізія з expectedVersion |
| `GET /v1/projects/:id/revisions` | Історія та diff references |
| `POST /v1/projects/:id/archive` | Архівування, без негайного видалення artifacts |
| `GET/POST /v1/agents` | Каталог профілів |
| `POST /v1/agents/:id/versions` | Нова версія профілю |
| `GET/POST /v1/connections` | Підключення; тільки secret references у відповідях |
| `POST /v1/connections/:id/probe` | Перевірка доступності, версії та capabilities |
| `POST /v1/routing/preview` | Рекомендації, пояснення та обмеження без виконання задачі |
| `POST /v1/plans/propose` | Створення пропозиції плану; окремий облік usage |
| `POST /v1/runs/preflight` | Повна перевірка snapshot, команди, прав, ресурсів |
| `POST /v1/runs` | Старт конкретної ProjectRevision та прийнятого плану |
| `GET /v1/runs/:id` | Snapshot стану з event cursor і version |
| `POST /v1/runs/:id/commands` | pause, resume, cancel, fork з command receipt |
| `POST /v1/runs/:id/plan-changes/preview` | Оцінка впливу перепланування |
| `POST /v1/runs/:id/plan-changes` | Прийняття зміни з expected plan revision |
| `GET /v1/runs/:id/tasks` | Граф і task state з pagination/filter |
| `POST /v1/tasks/:id/commands` | retry, cancel subtree, reassign-next-attempt |
| `GET /v1/tasks/:id/attempts` | Спроби й provenance результатів |
| `POST /v1/sessions/:id/messages` | Steering або доставка до наступного invocation |
| `GET /v1/runs/:id/events` | SSE; cursor та reconnect |
| `GET /v1/runs/:id/usage` | Фактичне/оцінене/невідоме usage і резерви |
| `GET /v1/artifacts/:id` | Metadata та авторизоване завантаження |
| `POST /v1/approvals/:id/decision` | Рішення з expected action hash |
| `GET /v1/operations/:id` | Стан довгої команди та її результат |

Артефактний URI не є дозволом на завантаження. Сервер перевіряє доступ до Run. Списки великих подій і payload мають ліміти; live token chunks можна агрегувати, але доменні transitions не відкидаються.

Помилки мають `{code, message, details, correlationId}`. Семантика: `400` некоректний запит; `401/403` доступ; `404` відсутність; `409` версія/стан конфліктує; `422` невиконуваний план; `429` перевищення квоти; `503` недоступний runtime. Секрети й raw provider stack не потрапляють у клієнтські помилки.

## 7. Внутрішній worker protocol

Внутрішні маршрути `/internal/v1/workers/*` відокремлені від користувацького API. Worker реєструє capabilities, отримує claim, renew lease, надсилає event batch, result або failure та читає control intents. Кожна зміна потребує `workerId`, `jobId`, `leaseEpoch` і message ID для дедуплікації.

Зареєстрований локальний worker має окремий короткоживучий credential. Майбутній віддалений worker потребує TLS, scoped registration і окремої політики передачі секретів/артефактів. Публічний API не дозволяє клієнту імітувати завершення worker job.

## 8. Локальний доступ та доставка подій

Майбутня вебпанель і API працюють на одному origin. Для браузера пропонується локальна pairing-процедура та HttpOnly session cookie, перевірка Origin/Host і CSRF для мутацій. CLI використовує scoped bearer token. UI не зберігає admin token у localStorage; порт не відкривається назовні автоматично.

SSE event містить `id`, `type`, `schemaVersion`, `runId`, `runSequence`, `payload`. Snapshot повертає узгоджений cursor, щоб наступний stream не втратив події. При простроченому retention cursor сервер вимагає resync snapshot. Slow client отримує обмежений буфер і reconnect; завершення задачі не залежить від наявності відкритої вкладки.
