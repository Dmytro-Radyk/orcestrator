# Архітектура Orcestrator

Статус: проєкт цільової архітектури для наступної реалізації. Дата: 2026-11-10.

Вимоги користувача: створення та редагування проєктів; підбір відповідних агентів; кілька агентів на одну задачу; паралельні задачі; субагенти та керування ними; інтеграція як API моделей, так і встановлених CLI-агентів; широкий функціонал.

Поточний код `src/` — експериментальний прототип. Описані тут нові модулі, таблиці, контракти та екрани ще не реалізовані. Документи визначають структуру подальшої роботи; вони не означають, що інтеграції або гарантії вже працюють.

## Базові рішення

1. Початковий сценарій — один користувач на локальному Windows-комп'ютері; Linux та командний режим враховані в межах модулів.
2. Локальна вебпанель, сервер керування, виконавець і CLI-клієнт. Desktop-оболонка може з'явитися пізніше без зміни доменної моделі.
3. Модульний моноліт для керування; запуск моделей і CLI — в окремому процесі worker. Не розділяємо кожен модуль на самостійний мережевий сервіс.
4. TypeScript для нової реалізації; поточний JavaScript-прототип зберігається до перенесення перевірених сценаріїв.
5. SQLite та локальні артефакти для одного хоста. PostgreSQL і віддалені workers — окремий наступний режим, не обов'язкова інфраструктура першого запуску.
6. Проєкт та його зміни мають ревізії; кожний запуск і кожна спроба фіксують точні вхідні дані та вибір агентів.
7. Агент пропонує план, інструментальний виклик або делегування; перевірку дозволів та зміну станів виконує програмний контролер.
8. «Найкращий агент» визначається вимогами задачі, політикою користувача і виміряними результатами; у каталозі немає незмінного рейтингу брендів.

## Приклад цільового сценарію

Користувач відкриває існуючий проєкт і задає зміну: «Додати авторизацію». Оркестратор пропонує аналітика, backend-агента, frontend-агента та рецензента. Після плану два виконавці працюють паралельно в окремих робочих каталогах. Backend-агент делегує перевірку міграції субагенту з вужчими правами. Рецензент оцінює конкретні зміни й результати тестів. Інтегратор перевіряє об'єднаний результат. Користувач бачить diff, витрати, журнал рішень та стан приймання.

Цей самий механізм підтримує некодові проєкти: дослідження, документи й аналіз даних. Для них результатами є артефакти та звіти, а Git-інтеграція не використовується.
