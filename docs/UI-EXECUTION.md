# Реальне виконання з панелі

`npm run ui` запускає статичну панель, планувальник і ядро виконання в одному локальному процесі на `127.0.0.1:4311`. Окремий `npm start` для панелі не потрібний; його CLI API залишається самостійним режимом.

**Оновлення 15.11.2026:** нові запуски й планування тепер проходять перевірку каталогу та політики без додаткових списань. Спочатку відкрийте «Підключення». Codex повертає підписку, моделі й квоти, але поки не підтверджує межу лише включеного використання; його нові виклики заблоковані. Описаний нижче сценарій виконання потребує дозволеного маршруту. Попередній живий запуск залишається історичним доказом роботи виконавця, а не доказом поточного дозволу на запуск. [Поточний стан каталогу](MODEL-REGISTRY.md).

## Робочий сценарій

Планування тепер може використовувати anonymous free-маршрут OpenCode. Автоматичні точні призначення реалізовано окремим серверним API, який ще потрібно зв'язати з екраном команди та виконанням. OpenCode поки не записує файли; його текстові результати не видаються за виконання file-editing задач. [Контракт](AI-DIRECTOR.md).

1. Створіть проєкт через майстер і прийміть план та рекомендації команди.
2. Натисніть «Запустити з Codex». Перед запуском видно фактичну модель, доступ для кожної ролі та папку проєкту. Рекомендації планувальника залишаються збереженими окремо.
3. Оберіть Codex з `workspace-write` для створення файлів або `read-only` для перевірки без запису. Якщо рецензент має записати звіт у файл, йому також потрібний `workspace-write`.
4. Після «Запустити Codex» сервер фіксує незмінний знімок плану й фактичних виконавців. Залежності, ліміт викликів, пауза та скасування обробляються ядром `Engine`.
5. Журнал оновлюється опитуванням сервера раз на 1,5 секунди: повідомлення агента, команди, їхній вивід і зміни файлів. «Результати» містять звіти агентів і маніфест файлів; «Запуски» — окрему історію зі знімками.

Пауза припиняє видачу наступних викликів; активний виклик завершується. Скасування передає abort провайдеру та завершує дерево CLI-процесів. Уже внесені зміни файлів залишаються. Після перезапуску сервера активний запуск стає `interrupted`, без автоматичного повтору змін.

## Збереження і папки

- Сервер зберігає робочий простір, профілі, плани, ревізії, запуски та події в `.orchestrator/ui/state.json`. Браузерний localStorage — кеш і джерело одноразового перенесення, якщо сервер ще порожній. Надалі сервер є основним джерелом даних.
- Збереження має номер версії робочого простору; конфлікт між вкладками не перезаписує дані мовчки. Після повідомлення про конфлікт експортуйте незбережені зміни й оновіть сторінку.
- Папка проєкту призначається сервером: `.orchestrator/workspaces/<hash>/`. Вона повторно використовується в наступних запусках цього проєкту. Довільні зовнішні папки та worktree в цьому UI ще не підключені.
- Звіти агентів зберігаються у запуску. Маніфест до 200 файлів фіксує створення, зміну й видалення; файл до 1 MB має SHA-256. Завантаження повертає **поточну** текстову версію з папки, а не історичну копію. Великі й бінарні файли переглядайте безпосередньо в папці.
- `.env*`, ключові файли, службові каталоги та symlink не включаються до маніфесту. Обробник завантаження перевіряє realpath і межі папки. `.orchestrator/` та `.env.local` виключені з Git.

## Codex і статус результату

Використовується збережений вхід Codex CLI. API-ключ для цього режиму не потрібний. Сервер задає executable сам; браузер не передає shell-команди чи шляхи до програм як конфігурацію виконавця.

Параметри `.env.local`:

```dotenv
ORCHESTRATOR_EXECUTOR_MODEL=gpt-6.1-sol
ORCHESTRATOR_EXECUTOR_REASONING=high
# ORCHESTRATOR_EXECUTOR_COMMAND=/absolute/path/to/codex
```

Якщо executable не заданий, використовується команда планувальника, а потім `codex` із PATH. Передаються `--sandbox`, `--ephemeral`, `--ignore-user-config` і серверна JSON Schema. Глобальні MCP, hooks і налаштування інструментів не успадковуються з config.toml. На Windows виконавець віддає перевагу штатному MXC, з `elevated` як legacy fallback; для перевіреної конфігурації потрібний Codex CLI 0.167.0+. Налаштування користувача не переписуються. Планувальник залишається окремим read-only викликом. Обмеження sandbox не обходяться.

Фінальний звіт виконавця має `status: completed | blocked | failed`, `summary`, `files`, `checks`. Для кожної перевірки записується `required`. `blocked`, `failed`, непроведені або провалені **обов’язкові** перевірки дають помилку задачі й блокують залежні задачі. Помилка необов’язкової діагностики залишається у звіті та не блокує виконані вимоги. Це перевірка протоколу та звіту агента, не незалежний доказ якості: критерії потрібно перевіряти тестами й окремим оглядом. Сам exit code 0 CLI не є достатньою умовою успіху.

## Поточні межі

UI виконує задачі через Codex. API, Claude Code та Ollama є окремими адаптерами ядра, але вибір цих виконавців у панелі ще не підключений. Кілька ролей у задачі виконуються pipeline; CLI в одній фізичній папці серіалізуються. Автоматичне делегування для запусків UI наразі вимкнене. Грошові ліміти, незалежний evaluator результату, відновлення виконання, інкрементальне перепланування та ізольовані worktree залишаються наступними етапами.

Налаштований Codex не гарантує працездатності його sandbox. Якщо запуск повертає `helper_unknown_error: setup refresh had errors`, діагностуйте штатну Windows-інсталяцію; не змінюйте результат на успішний і не вимикайте sandbox. [Офіційна документація Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox), [неінтерактивний Codex](https://learn.chatgpt.com/docs/non-interactive-mode).

## Перевірений результат

Фінальний живий запуск від 10.11.2026: прийнятий AI-план із двох задач виконано через Codex CLI з `gpt-6.1-sol`, окремими ролями розробника та рецензента, без глобальних MCP. Створено `slugify.mjs`, тести, README та незалежний `REPORT.md`; підсумковий звіт містить PASS і 36 успішних тестів. Пауза черги та її продовження перевірені в UI, скасування — інтеграційними тестами.

15.11.2026 повторно пройшли 38 тестів оркестратора та 36 тестів створеного проєкту. Після запуску нового процесу сервера панель відновила завершений запуск, його знімок, журнал і маніфест файлів. Історичний звіт відкривається без зміни поточного плану.

Скріншот перевірки з локальним шляхом і персональним usage зберігається тільки локально.
