# Реальне виконання з панелі

`npm run ui` запускає статичну панель, планувальник і ядро виконання в одному локальному процесі на `127.0.0.1:4311`. Окремий `npm start` для панелі не потрібний; його CLI API залишається самостійним режимом.

**Оновлення 15.11.2026:** нові запуски й планування тепер проходять перевірку каталогу та політики без додаткових списань. Спочатку відкрийте «Підключення». Codex повертає підписку, моделі й квоти, але поки не підтверджує межу лише включеного використання; його виклики потребують виконання умов контрольованої підписки. Описаний нижче сценарій виконання потребує дозволеного маршруту. Попередній живий запуск залишається історичним доказом роботи виконавця, а не доказом поточного дозволу на запуск. [Поточний стан каталогу](MODEL-REGISTRY.md).

## Робочий сценарій

Концепція, план і підбір моделей використовують підтверджені маршрути. OpenCode створює файли через керований сервером worker. [Контракт AI-керівника](AI-DIRECTOR.md), [ізоляція, делегування та SSE](ISOLATED-EXECUTION.md).

1. Створіть проєкт у майстрі й прийміть план.
2. У вкладці «Команда» виконайте AI-підбір точних моделей. Для керованого запису достатньо `workspaceWrite`, без прямих інструментів.
3. Натисніть «Запустити AI-команду»: діалог показує збережений підбір і робочу папку. Без актуальної пропозиції можна призначити доступні маршрути вручну.
4. Сервер фіксує snapshot, виконує незалежні задачі в окремих worktree, перевіряє Node-тести й інтегрує результати. Конфлікт блокує інтеграцію.
5. Події надходять через SSE без періодичного опитування. 3D-сцена та її камера зберігаються. Вкладки результатів та запусків містять фактичні звіти й маніфести.

Пауза зупиняє видачу нових викликів і дозволяє активним завершитися. Скасування abort-ить процеси; незавершений candidate не приймається. Уже інтегровані файли залишаються. Перезапуск сервера позначає активний запуск `interrupted` без повторного виконання.

## Збереження і папки

- Сервер зберігає робочий простір, профілі, плани, ревізії, запуски та події в `.orchestrator/ui/state.json`. Браузерний localStorage — кеш і джерело одноразового перенесення, якщо сервер ще порожній. Надалі сервер є основним джерелом даних.
- Збереження має номер версії робочого простору; конфлікт між вкладками не перезаписує дані мовчки. Після повідомлення про конфлікт експортуйте незбережені зміни й оновіть сторінку.
- Папка проєкту призначається сервером: `.orchestrator/workspaces/<hash>/`. Вона повторно використовується в наступних запусках цього проєкту. Worktree задач розміщені в приватному `.orchestrator/workspaces/.runs/`. Довільні зовнішні папки через UI не приймаються.
- Звіти агентів зберігаються у запуску. Маніфест до 200 файлів фіксує створення, зміну й видалення; файл до 1 MB має SHA-256. Завантаження повертає **поточну** текстову версію з папки, а не історичну копію. Великі й бінарні файли переглядайте безпосередньо в папці.
- `.env*`, ключові файли, службові каталоги та symlink не включаються до маніфесту. Обробник завантаження перевіряє realpath і межі папки. `.orchestrator/` та `.env.local` виключені з Git.

## Codex і статус результату

Використовується збережений вхід Codex CLI. API-ключ для цього режиму не потрібний. Сервер задає executable сам; браузер не передає shell-команди чи шляхи до програм як конфігурацію виконавця.

Параметри `.env.local`:

```dotenv
ORCHESTRATOR_EXECUTOR_MODEL=gpt-6.1-sol
ORCHESTRATOR_EXECUTOR_REASONING=high
# ORCHESTRATOR_EXECUTOR_COMMAND=/absolute/path/to/codex
```

Якщо executable не заданий, використовується команда планувальника, а потім `codex` із PATH. Передаються `--sandbox`, `--ephemeral`, `--ignore-user-config` і серверна JSON Schema. Глобальні MCP, hooks і налаштування інструментів не успадковуються з config.toml. На Windows виконавець віддає перевагу штатному MXC, з `elevated` як legacy fallback; для перевіреної конфігурації потрібний Codex CLI 0.167.0+. Налаштування користувача не переписуються. Планувальник залишається окремим read-only викликом. Обмеження sandbox не обходяться.

Фінальний звіт Codex-виконавця має `status: completed | blocked | failed | delegated`, `summary`, `files`, `checks`. Для кожної перевірки записується `required`. `blocked`, `failed`, непроведені або провалені **обов’язкові** перевірки дають помилку задачі й блокують залежні задачі. Помилка необов’язкової діагностики залишається у звіті та не блокує виконані вимоги. Це перевірка протоколу та звіту агента, не незалежний доказ якості: критерії потрібно перевіряти тестами й окремим оглядом. Сам exit code 0 CLI не є достатньою умовою успіху.

## Скіли й MCP для задач

В ізольованій робочій копії Codex автоматично отримує MCP `project_computer`. Інструмент `inspect_preview` відкриває статичну сторінку проєкту в Chromium і повертає знімок та діагностику верстки. Коли доступний Docker Desktop, `run_node_tests` і `run_project_check` запускають Node.js, Chromium та PostgreSQL перевірки у тимчасовому Linux-контейнері. Для серверної перевірки `scripts/test-storefront-postgres.mjs` тимчасове середовище запускає `src/server.mjs` і чекає відповіді від `/healthz`.

Версію Node.js оркестратор читає з `package.json` (`engines.node`, `volta.node`), `.nvmrc`, `.node-version` і статичного офіційного образу в `Dockerfile`. Для PostgreSQL використовує версію офіційного образу в Compose. Якщо вимоги задаються інакше, проєкт може записати `{"node":"22","postgres":"16"}` у `.orcestrator-runtime.json`. Відсутні вимоги мають стандартні значення Node.js 24 і PostgreSQL 17. Версії перевірок зберігаються в журналі. Взаємовиключні вимоги повертаються виконавцю як діагностика для узгодження.

Оркестратор підхоплює обов’язкові перевірки підтримуваних форматів зі звіту задачі та записує результат у журнал. Якщо тест повертає помилку перевірки, оркестратор передає діагностику призначеному Codex-виконавцю для виправлення в межах бюджету запуску. Конфлікт перевіреної чернетки передається на узгодження в окрему робочу копію.

Оркестратор зіставляє назву, мітки та початок опису задачі з правилами розширень. Якщо встановлено `ui-ux-pro-max`, він автоматично доступний для задач з інтерфейсом. Виконавець отримує обмежений витяг одного скіла. Для Gemini та OpenCode він входить у текстовий контекст із пріоритетом файлів проєкту.

Перед викликом вбудований хук `workspace-checks` читає `package.json` поточної робочої копії та передає до шести наявних команд перевірки або збірки. Сам хук не виконує скрипти. У «Активності» журнал показує підключений хук, час у черзі, підготовку виклику та тривалість виконання. Вбудовані хуки оркестратора працюють окремо від глобальних хуків Codex, для яких діє штатний перегляд і довіра через `/hooks`. [Хуки Codex](https://learn.chatgpt.com/docs/hooks)

Локальний файл `.orchestrator/ui/task-extensions.json` задає власний список скілів та MCP-серверів. Відсутнє поле `skills` зберігає стандартне правило для UI/UX. Порожній список `skills` вимикає підбір. Правила перечитуються на наступній задачі.

Перед викликом оркестратор перевіряє підготовлені MCP через ініціалізацію, а записи `services` через `GET` на їхню `healthUrl`. Запис `services` має `id`, `terms` і `healthUrl`. Для локального MCP або API поле `start` може вказувати абсолютний шлях `executable`, масив `args` та робочу папку `cwd`. Оркестратор запускає цю програму, коли локальне підключення не відповідає, і чекає на готовність. Поле MCP `fallback` містить ідентифікатори дозволених резервів. Резерв отримує лише список інструментів основного підключення і зберігає свій ідентифікатор. Результат відновлення з’являється в журналі задачі.

```json
{
  "skills": [
    {"id": "ui-ux-pro-max", "terms": ["frontend", "ui", "ux", "дизайн", "інтерфейс"]}
  ],
  "mcpServers": [
    {"id": "project_docs", "terms": ["project-docs"], "url": "http://127.0.0.1:3000/mcp", "tools": ["search", "read"]}
  ]
}
```

Для скіла шлях за замовчуванням `skills/<id>/SKILL.md` відносно `CODEX_HOME`. Поле `path` дозволяє вказати інший `SKILL.md` з каталогів `skills` або `plugins/cache` у цьому ж корені. Увімкнені лише інструкції файлу. Доступ до допоміжних скриптів визначає середовище виконавця.

Приклад MCP потребує запущеного HTTP MCP-сервера та його фактичних назв інструментів. Оркестратор передає Codex лише явно названі сервери й інструменти, які збіглися з поточною задачею. Запис про MCP-виклик містить назву сервера, інструмента й статус. Права на зовнішні дії задаються також на боці MCP-сервера. Закриті конектори Codex Desktop, налаштування авторизації та плагіни з довільними процесами через цей файл не імпортуються. [Параметри Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

## Поточні межі

UI підтримує підтверджені Codex та OpenCode маршрути; Codex inference потребує підтверджених умов контрольованої підписки. API, Claude Code та Ollama не підключені як дозволені виконавці панелі. Увімкнені bounded delegation, ізольовані worktree та SSE. Автоматичний runner керованого worker підтримує Node-тести. Незалежний evaluator якості, продовження перерваного виконання, перепланування та очищення worktree залишаються наступними етапами.

Налаштований Codex не гарантує працездатності його sandbox. Якщо запуск повертає `helper_unknown_error: setup refresh had errors`, діагностуйте штатну Windows-інсталяцію; не змінюйте результат на успішний і не вимикайте sandbox. [Офіційна документація Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox), [неінтерактивний Codex](https://learn.chatgpt.com/docs/non-interactive-mode).

## Перевірений результат

Фінальний живий запуск від 10.11.2026: прийнятий AI-план із двох задач виконано через Codex CLI з `gpt-6.1-sol`, окремими ролями розробника та рецензента, без глобальних MCP. Створено `slugify.mjs`, тести, README та незалежний `REPORT.md`; підсумковий звіт містить PASS і 36 успішних тестів. Пауза черги та її продовження перевірені в UI, скасування — інтеграційними тестами.

15.11.2026 повторно пройшли 38 тестів оркестратора та 36 тестів створеного проєкту. Після запуску нового процесу сервера панель відновила завершений запуск, його знімок, журнал і маніфест файлів. Історичний звіт відкривається без зміни поточного плану.

Скріншот перевірки з локальним шляхом і персональним usage зберігається тільки локально.


15.11.2026 окремо перевірено актуальний безкоштовний цикл: AI-підбір, паралельні OpenCode file workers, інтеграція та незалежна read-only перевірка. Усі 12 тестів створеного clamp-проєкту пройшли в sandbox; вартість кожного модельного виклику — 0. Деталі у [контракті виконання](ISOLATED-EXECUTION.md).


Актуальні умови використання Codex за підпискою: [контроль квоти та білінгу](CODEX-SUBSCRIPTION.md).
