# Створення проєкту з AI

Майстер: **задум → концепція (необов'язково) → детальний план → підбір команди → створення проєкту**.

З 15.11.2026 усі нові AI-запити перевіряються політикою без додаткових списань. Автоматичний керівник обирається з підтвердженого каталогу; підключено anonymous free-моделі OpenCode для концепції та плану. Codex усе ще блокується через непідтверджену межу платних кредитів. Старий етап `team` зберігає контракт профілів; новий API точних routeIds ще потребує інтеграції в екран команди. Демо залишається окремою явною дією. [Контракт AI-керівника](AI-DIRECTOR.md), [каталог та політика](MODEL-REGISTRY.md).

1. «Допоможіть продумати ідею»: модель пропонує концепцію, ключові функції, відкриті питання й ризики. Користувач може відредагувати концепцію, дати відповіді та повторно уточнити її.
2. «Проєкт уже придуманий»: стадія концепції пропускається, готовий опис переходить у планування.
3. Планувальник створює задачі, інструкції, залежності, необхідні навички, критерії готовності, припущення та ризики. Перед прийняттям можна редагувати задачі.
4. Після прийняття плану модель обирає профілі/моделі з каталогу для кожної задачі та пояснює рішення. Кілька агентів на задачу допустимі. Ручне коригування є додатковою дією, а не обов'язковим вибором усієї команди.

Ідея, план, призначення та provenance зберігаються разом із локальним проєктом. У деталях задачі видно критерії готовності й причину вибору команди.

## Налаштування справжнього планувальника

Сервер використовує одну явно налаштовану модель для трьох окремих операцій: `idea`, `plan`, `team`. Це роль планувальника/маршрутизатора, а не модель, яка обов'язково виконуватиме всі задачі. Склад команди визначається відповіддю моделі на основі прийнятого плану, каталогу профілів та пріоритету користувача.

`npm run ui` автоматично читає `.env.local` у корені репозиторію. Можна скопіювати `.env.example` у `.env.local` і за потреби вказати шлях до native Codex executable. Змінні, встановлені в середовищі запуску, мають пріоритет. `.env.local` виключено з Git; файл не роздається статичним сервером. Наявна авторизація CLI використовується повторно, API-ключ для цього режиму не потрібний.

Наприклад, API-планувальник (ключ задайте у своєму середовищі, не у JSON проєкту):

```powershell
$env:ORCHESTRATOR_PLANNER_PROVIDER = 'responses'
$env:ORCHESTRATOR_PLANNER_MODEL = 'gpt-6-astra'
# OPENAI_API_KEY має бути налаштована в середовищі цього процесу.
npm run ui
```

Для API використовується наявний адаптер Responses. Модель повинна бути доступною вашому акаунту; її назву можна змінити. Вибір моделі для складного планування слід оцінювати на проєктах користувача. [OpenAI text generation](https://developers.openai.com/api/docs/guides/text).

Через встановлений та авторизований Codex CLI:

```powershell
$env:ORCHESTRATOR_PLANNER_PROVIDER = 'codex'
$env:ORCHESTRATOR_PLANNER_MODEL = 'gpt-6-astra'
$env:ORCHESTRATOR_PLANNER_REASONING = 'high'
npm run ui
```

Назва моделі має підтримуватися вашим CLI й акаунтом. Codex запускається з `--sandbox read-only`, `--ephemeral`, `--ignore-user-config`: збережений вхід залишається доступним, користувацький config.toml не завантажується, файли сесії не зберігаються. Робоча папка — `.orchestrator/planner/`. Це окремий каталог для планування, а не повна ізоляція читання файлової системи. Prompt забороняє виконувати задачі й використовувати інструменти; CLI залишається агентним середовищем.

Для кожної стадії сервер передає власну JSON Schema (`scripts/schemas/`). Фінальне повідомлення перевіряється також валідаторами DAG і каталогу; проміжні повідомлення CLI не потрапляють у JSON. `ORCHESTRATOR_PLANNER_REASONING` задає рівень міркування Codex (типово `high`), який видно в майстрі та provenance. Автоматичної заміни моделі при помилці немає.

Додаткові налаштування: `ORCHESTRATOR_PLANNER_COMMAND` — executable Codex; `ORCHESTRATOR_PLANNER_BASE_URL` — адреса API; `ORCHESTRATOR_PLANNER_KEY_ENV` — назва змінної ключа (типово `OPENAI_API_KEY`). Для сумісного Chat Completions можна задати provider `chat` та його endpoint/model. Після зміни environment або `.env.local` перезапустіть сервер.

## Демонстрація та межі

- Без конфігурації реальні AI-кнопки недоступні. «Показати демо-приклад» окремо створює навчальний шаблон. Підбір у цьому режимі працює за збігом навичок і так підписаний. Помилка реального AI-запиту не підміняється демо-відповіддю.
- Валідація перевіряє структуру, DAG, критерії, повноту призначень і належність агентів до каталогу. Якість плану потребує змістовного перегляду користувачем.
- Модель отримує лише профілі з каталогу. Вона не встановлює нові CLI й не підключає невідомі провайдери. Ціни й доступність не вигадуються; наразі каталог не має перевірених eval/цін/health, тому рекомендація умовна.
- Налаштований endpoint означає наявність конфігурації, не гарантію доступу до моделі. 10.11.2026 пройдено живий браузерний сценарій через авторизований Codex CLI, `gpt-6-astra`, reasoning `high`: концепція Orbit Notes → план із 5 задачами та паралельними гілками → рекомендації з 1–2 профілів на задачу → створення проєкту. Це перевірка інтеграції на одному прикладі, а не порівняльна оцінка моделей або підтвердження доступності всіх профілів.
- Планування: один зовнішній виклик на операцію, до 240 секунд та 12000 output tokens для HTTP API; один активний запит на сервер. Native CLI має власний внутрішній цикл і облік. Вартість залежить від зовнішнього провайдера; грошового ліміту в цьому endpoint поки немає.
- Запити same-origin з короткоживучим серверним token; секрети залишаються на сервері. Закриття майстра скасовує очікування запиту. Уже надісланий запит може мати фактичне usage навіть після скасування.
- Це локальна інтеграція планування поверх UI-прототипу. Черга durable planning Run, база даних, відновлення планування після перезапуску та повна модель permissions із цільової архітектури ще попереду.
- Після планування можна налаштувати фактичних Codex-виконавців і запустити задачі з панелі. Рекомендована команда та реальні призначення зберігаються окремо. Див. [реальне виконання](UI-EXECUTION.md).
