# Створення проєкту з AI

Майстер: **керівник і задум → концепція (необов'язково) → детальний план → точні моделі команди → створення проєкту**.

## Послідовність

1. Опишіть проєкт. Типово AI підбирає модель за сферою, складністю та вимогами проєкту — окремо для ідеї та детального плану. Ручне закріплення доступне в додаткових налаштуваннях; недоступна явно закріплена модель не підміняється іншою.
2. «Допоможіть продумати ідею» відкриває опрацювання концепції, функцій, питань та ризиків. Концепцію можна редагувати й уточнювати повторно. «Проєкт уже придуманий» пропускає цей етап.
3. Прийміть або відредагуйте детальний план: задачі, інструкції, залежності, навички й критерії готовності. За потреби для задачі можна обрати аналіз без зміни файлів; типовий режим — робота з файлами.
4. Керівник отримує актуальний каталог і обирає точні маршрути моделей для кожної задачі. Майстер показує моделі, провайдерів, підтверджений тариф і пояснення вибору.
5. «Створити проєкт» повторно перевіряє доступ і зберігає проєкт разом із призначенням моделей. До підтвердження створення робочий простір не змінюється. Помилка залишається в майстрі для повторного підбору або спроби збереження.
6. Відкрийте запуск і підтвердьте показану команду. Повторний AI-підбір після створення не потрібен. Це окреме підтвердження виконання й файлових змін; саме планування задачі не виконує.

Автоматичний режим використовує окремий AI-запит вибору з дозволеного каталогу, описом проєкту, концепцією, уточненнями й метою етапу. Типова доступна модель лише проводить цей вибір. Сервер перевіряє точний ID, пояснення та повторно перевіряє доступ після відповіді. Невідома або недоступна обрана модель зупиняє запит без прихованої підміни. Коли доступний один кандидат, додаткового AI-виклику вибору немає.

Назва фактичної моделі й пояснення показуються разом із результатом. Модель прийнятого плану далі підбирає виконавців і успадковується для відновлення; окреме налаштування проєкту має пріоритет. Для ручного режиму одна закріплена модель веде всі етапи. [Відновлення](AUTOMATIC-RECOVERY.md).

Якщо автоматично підібраний керівник після планування втратив доступ або включену квоту, підбір команди може переобрати керівника серед дозволених моделей за тим самим прийнятим планом. Це вмикається `allowManagerFallback: true` лише для автоматичного режиму майстра. Для ручного закріплення прихованої підміни немає. Пропозиція й запуск зберігають точний маршрут нового керівника, а provenance — причину заміни та usage модельних викликів добору.

Це обґрунтований AI-вибір за доступними метаданими, а не виміряний рейтинг моделей. Ціни, evals і гарантії якості не вигадуються. Результат зберігає `provenance.selection`: етап, пояснення, модель, яка робила вибір, та її usage. Додатковий модельний виклик добору враховується окремо від генерації ідеї/плану й від виконання задач.

## Політика моделей

Дозволені підтверджені безкоштовні маршрути та доступ, включений у наявні підписки. Metered API, додаткові кредити й невідомі умови списань блокуються. Наявність підписки сама по собі не доводить доступність кожної моделі. [Каталог і політика](MODEL-REGISTRY.md), [Codex](CODEX-SUBSCRIPTION.md), [Antigravity / Gemini](ANTIGRAVITY-GEMINI.md).

У налаштуваннях команди можна обмежити виконавців лише безкоштовними моделями та дозволити від 1 до 6 моделей на задачу. Типово використовується максимум одна модель; кілька моделей потребують обґрунтування керівника. Тариф виконавців не змінює тариф обраного керівника.

«Показати демо-приклад» залишається окремою явною дією. Демо використовує рольові профілі й правила та не створює справжнього AI-призначення. Помилка реального AI-запиту не підміняється демо.

## Налаштування

Запуск: `npm run ui`. Сервер читає `.env.local`; змінні процесу мають пріоритет. Шляхи native CLI та необов'язковий маршрут за замовчуванням описані в `.env.example`. Для штатного входу CLI API-ключ не потрібний. `.env.local`, авторизація та дані `.orchestrator/` виключені з Git.

Планування панелі використовує каталог через `execution.director`, а не старі `ORCHESTRATOR_PLANNER_PROVIDER` / `ORCHESTRATOR_PLANNER_MODEL`. Низькорівневі адаптери й legacy-операція `team` залишаються для сумісності; майстер використовує точні серверні маршрути.

## Контракт і збереження

- `GET /api/planning/status` повертає токен планування, поточну модель і `managerRoutes` — доступні маршрути зі структурованим виводом. Параметр `managerRouteId` дозволяє перевірити конкретного керівника.
- `POST /api/planning`: `{ kind: "idea" | "plan", input, managerRouteId? }`. Без закріплення сервер виконує проєктний AI-підбір, з ним — перевіряє ручний маршрут. Концепція та план проходять валідацію структури, залежностей і критеріїв. `GET /api/planning/status` повідомляє `selectionMode: "project"`; модель у статусі є початковим доступним керівником, а не результатом підбору під ще невідомий проєкт.
- `POST /api/routing/draft`: `{ name, description, plan, managerRouteId?, priority, maxAgentsPerTask, requirements }`. Повертає серверну AI-пропозицію з точними маршрутами, fingerprint та строком дії. Це не створює проєкт і не запускає виконавців.
- `PUT /api/workspace`: звичайні `revision`, `workspace`, а для створення з командою — `routingDraftId` та `routingProjectId`. Сервер звіряє план, новий ID проєкту, доступність і тариф моделей та повторно перевіряє ревізію після сканування. Призначення й робочий простір зберігаються однією операцією; draft споживається одноразово.
- Після створення `/api/routing` і `/api/execution/preview` повертають уже прийняте призначення. Запуск використовує його `proposalId`. [Контракт керівника](AI-DIRECTOR.md).

Неприйнятий підбір зберігається лише в пам'яті сервера до 30 хвилин; одночасно утримуються максимум 20 пропозицій. Після перезапуску або втрати пропозиції потрібно повторити підбір команди. Прийнятий проєкт і призначення зберігаються у локальному сховищі.

Під час підбору команди через UI Codex отримує JSON Schema з точними ID дозволених маршрутів та задач. Сервер окремо перевіряє допустимість кожного маршруту для конкретної задачі. Якщо відповідь некоректна або каталог змінився під час очікування, допускається один автоматичний повтор: керівник отримує діагностику й новий каталог з тими самими вимогами до тарифу та можливостей. Після повтору результат знову перевіряється; довільна підміна моделі або послаблення політики не застосовуються. `provenance.attempts` зберігає модель і usage кожного виклику, `repairCount` — кількість виправлень. Автоматичне відновлення виконуваних задач має власні правила й бюджет; цей UI-повтор до нього не додається.

Майстер зберігає задум, концепцію й план у `sessionStorage` цієї вкладки. Після перезавантаження чернетка відкривається на останньому змістовному етапі; старе серверне призначення відкидається, щоб повторно підібрати актуальну команду. Після успішного створення проєкту чернетка очищається. Це не серверна резервна копія: закриття вкладки або очищення браузерних даних може видалити її.

## Перевірки та межі

Автоматичні перевірки покривають ідею → план → точні безкоштовні виконавці під керуванням підписної моделі → збереження → виконання без повторного підбору, пропуск концепції, зміну плану, недоступність моделі, зміну тарифу, одноразове прийняття та паралельну зміну ревізії. Провайдери в цих тестах повертають контрольовані відповіді; реальні AI-моделі не викликаються.

Після додавання проєктного автопідбору пройшли 160 автоматичних тестів. Окремий живий API-запит для невеликого локального списку задач із пріоритетом економії завершився успішно: GPT-6.1 Sol обрав GPT-6 Luna за описом проєкту, Luna повернула концепцію. Збережено модель, етап і пояснення вибору. Це перевірка автоматичного добору для ідеї; живий детальний план у цьому проході не генерувався. Файли проєкту й задачі виконання не створювалися; сирий результат зберігається лише локально поза Git.

Після виправлення маршрутизації пройшов повний набір зі 171 тесту. Окремий живий підбір через Codex GPT-6.1 Sol призначив трьом контрольним задачам дозволені безкоштовні маршрути DeepSeek V4.1 Flash Free та GLM-5.3-Flash Free. Відповідь пройшла перевірку з першої спроби; файли проєкту не створювалися, самі задачі не виконувалися. Сценарій вичерпання квоти керівника та його переобрання перевірено контрольованими HTTP-тестами; під час цього живого проходу Codex уже був доступний, заміна не знадобилася.

У браузері перевірено збереження тестової чернетки: введено опис, показано демо-план із п’яти задач, вручну змінено підсумок, перезавантажено вкладку й повторно відкрито майстер. Відновилися підсумок, задачі, інструкції та критерії. Новий серверний проєкт у цьому сценарії не створювався. Це перевірка відновлення чернетки, а не живий повний прохід великого користувацького проєкту. Попередні перевірки виконання описані окремо в [звіті](RELEASE-VALIDATION.md).

Планування допускає один активний запит концепції/плану та один окремий підбір draft-команди. Фіксованого загального ліміту очікування для ідеї, плану й ручного AI-підбору команди немає: `/api/planning/status` повертає `timeouts: { idea: null, plan: null, team: null }` та зайнятість планувальника. Очікування зупиняється кнопкою, закриттям майстра або розривом з’єднання. У Antigravity використовується документований `--print-timeout 0s`, який очікує завершення turn; зовнішній сигнал скасування залишається активним.

Перевірки доступу й квот продовжують працювати та мають власні мережеві дедлайни. Відповідь провайдера з помилкою або таймаутом також залишається помилкою. Виконання задач і підбір заміни тепер також не мають фіксованого загального дедлайну за замовчуванням. За потреби оператор може явно задати `ORCHESTRATOR_EXECUTOR_TIMEOUT_MS` та `ORCHESTRATOR_RECOVERY_TIMEOUT_MS`; ліміт виклику виконавця починається після отримання слота, без часу очікування в черзі.

Usage планування зберігається у provenance й обліковується окремо від `run.calls` виконання. Закриття майстра перериває очікування модельного запиту, але вже використані токени можуть бути зараховані провайдером. Збереження проєкту після остаточного підтвердження є окремою операцією.

Якість плану потребує змістовного перегляду. Durable planning runs, відновлення незавершеного майстра після перезапуску та транзакційна база даних ще не реалізовані.

Звіт виконання Codex використовує strict JSON Schema: кожне поле об’єкта обов’язкове, зокрема `subtasks` та вкладене `agentIds`. Без делегування повертається `subtasks: []`; порожнє `agentIds` у дочірній задачі успадковує виконавця. Помилки з JSONL-потоку Codex читаються також при ненульовому exit code. Помилка схеми позначається `EXECUTION_SCHEMA_INVALID` і не запускає витратний AI-підбір іншого виконавця для тієї самої некоректної конфігурації.

Оновлення статусу запуску не перезаписує назву, інструкції, навички, залежності, критерії та профілі агентів редагованого плану. Перевірка незмінності плану під час recovery залишається активною; повідомлення уточнює ревізію або змінене поле. У зведенні помилок залежні задачі, які не запускалися, показуються окремим лічильником.

Після цих виправлень пройшли 178 автоматичних тестів, включно зі збереженням UI під час recovery та відхиленням справжніх змін інструкцій без підвищення ревізії. Живий діагностичний виклик Codex через підтверджену підписку створив один файл у відокремленій ігнорованій папці, перевірив його вміст і повернув успішний structured report. Це перевірка виконавця, а не повний запуск користувацького плану. У браузері перевірено компактне зведення попереднього невдалого запуску.
## Розподіл роботи між підписками

У режимі «Баланс якості та часу» сумісні задачі з одним виконавцем розподіляються між квотами Codex і Gemini. Оркестратор враховує підтверджене використання квоти й залишає AI-керівнику вибір моделі в межах сумісних маршрутів. Gemini з керованими файловими змінами підходить для текстових, документальних і частини фронтенд-задач. Вимоги до інструментів, типу доступу й тарифу застосовуються до розподілу. У режимі економії сумісні безкоштовні маршрути мають пріоритет.

У заблокованому запуску дія «Передати частину задач Gemini» повторно перевіряє каталог і змінює призначення сумісних нерозпочатих задач. Історія, готові результати й активні чернетки зберігаються. Дія не запускає моделей.
