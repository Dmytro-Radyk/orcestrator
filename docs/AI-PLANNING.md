# Створення проєкту з AI

Майстер: **задум → концепція (необов'язково) → детальний план → підбір команди → створення проєкту**.

1. «Допоможіть продумати ідею»: модель пропонує концепцію, ключові функції, відкриті питання й ризики. Користувач може відредагувати концепцію, дати відповіді та повторно уточнити її.
2. «Проєкт уже придуманий»: стадія концепції пропускається, готовий опис переходить у планування.
3. Планувальник створює задачі, інструкції, залежності, необхідні навички, критерії готовності, припущення та ризики. Перед прийняттям можна редагувати задачі.
4. Після прийняття плану модель обирає профілі/моделі з каталогу для кожної задачі та пояснює рішення. Кілька агентів на задачу допустимі. Ручне коригування є додатковою дією, а не обов'язковим вибором усієї команди.

Ідея, план, призначення та provenance зберігаються разом із локальним проєктом. У деталях задачі видно критерії готовності й причину вибору команди.

## Налаштування справжнього планувальника

Сервер використовує одну явно налаштовану модель для трьох окремих операцій: `idea`, `plan`, `team`. Це роль планувальника/маршрутизатора, а не модель, яка обов'язково виконуватиме всі задачі. Склад команди визначається відповіддю моделі на основі прийнятого плану, каталогу профілів та пріоритету користувача.

Наприклад, API-планувальник (ключ задайте у своєму середовищі, не у JSON проєкту):

```powershell
$env:ORCHESTRATOR_PLANNER_PROVIDER = 'responses'
$env:ORCHESTRATOR_PLANNER_MODEL = 'gpt-6-astra'
# OPENAI_API_KEY має бути налаштована в середовищі цього процесу.
npm run ui
```

Для API використовується наявний адаптер Responses. Модель повинна бути доступною вашому акаунту; її назву можна змінити. Вибір моделі для складного планування слід оцінювати на проєктах користувача. [OpenAI text generation](https://developers.openai.com/api/docs/guides/text).

Через встановлений та авторизований Codex CLI:

```powershell
$env:ORCHESTRATOR_PLANNER_PROVIDER = 'codex'
$env:ORCHESTRATOR_PLANNER_MODEL = 'gpt-6-astra'
npm run ui
```

Назва моделі має підтримуватися вашим CLI й акаунтом. Використовується read-only запуск; endpoint планувальника не виконує задачі створюваного проєкту. Додаткові налаштування: `ORCHESTRATOR_PLANNER_COMMAND` — executable Codex; `ORCHESTRATOR_PLANNER_BASE_URL` — адреса API; `ORCHESTRATOR_PLANNER_KEY_ENV` — назва змінної ключа (типово `OPENAI_API_KEY`). Для сумісного Chat Completions можна задати provider `chat` та його endpoint/model. Після зміни environment перезапустіть сервер.

## Демонстрація та межі

- Без конфігурації реальні AI-кнопки недоступні. «Показати демо-приклад» окремо створює навчальний шаблон. Підбір у цьому режимі працює за збігом навичок і так підписаний. Помилка реального AI-запиту не підміняється демо-відповіддю.
- Валідація перевіряє структуру, DAG, критерії, повноту призначень і належність агентів до каталогу. Якість плану потребує змістовного перегляду користувачем.
- Модель отримує лише профілі з каталогу. Вона не встановлює нові CLI й не підключає невідомі провайдери. Ціни й доступність не вигадуються; наразі каталог не має перевірених eval/цін/health, тому рекомендація умовна.
- Налаштований endpoint означає наявність конфігурації, не підтвердження доступу до моделі. Автентифікація, доступність та якість живих відповідей у поточній перевірці не тестувалися.
- Планування: один зовнішній виклик на операцію, до 120 секунд та 12000 output tokens для HTTP API; один активний запит на сервер. Native CLI має власний внутрішній цикл і облік. Вартість залежить від зовнішнього провайдера; грошового ліміту в цьому endpoint поки немає.
- Запити same-origin з короткоживучим серверним token; секрети залишаються на сервері. Закриття майстра скасовує очікування запиту. Уже надісланий запит може мати фактичне usage навіть після скасування.
- Це локальна інтеграція планування поверх UI-прототипу. Черга durable planning Run, база даних, відновлення планування після перезапуску та повна модель permissions із цільової архітектури ще попереду.
- Виконання створених задач у панелі залишається демонстраційним. Реальне планування і реальне виконання задач — різні можливості.
