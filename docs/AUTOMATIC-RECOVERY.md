# Автоматичне відновлення задач

Після завершення активних процесів невдалий запуск може попросити AI-керівника замінити виконавців лише невдалих задач. Відновлення зберігає той самий `run.id`, ревізію плану, залежності та прийняту папку. Успішні задачі не виконуються повторно. Дочірню задачу можна відновити окремо, після чого батько продовжить синтез без дублювання дітей.

## Налаштування

Нові запуски локальної панелі типово мають автоматичне відновлення з двома спробами. Проєкт підтримує:

```json
{
  "recovery": {
    "enabled": true,
    "maxAttempts": 2,
    "managerRouteId": "codex:gpt-6.1-sol"
  }
}
```

`maxAttempts` — від 1 до 3 раундів відновлення на весь запуск, додатково до початкового виконання. `managerRouteId` необов'язковий; без нього керівник обирається звичайною політикою з доступних маршрутів. Недоступний явно закріплений керівник не підміняється. Для CLI/core API потрібно явно задати `recovery.enabled: true` і `workspaceMode: isolated`. Скасовані й перервані перезапуском сервера запуски автоматично не відновлюються.

Якщо запуск панелі використовує збережену AI-пропозицію з явно вибраним керівником, його `managerRouteId` успадковується для відновлення. Окреме значення `project.recovery.managerRouteId` має пріоритет. Автоматичний вибір керівника не створює такого закріплення: під час відновлення політика може вибрати інший доступний маршрут.

Кожна спроба виклику керівника зараховується в `run.calls` і той самий `limits.maxCalls`, що й виконавці. Якщо бюджету не вистачає на керівника та повторну задачу з її обов'язковим reviewer, новий підбір не починається. За раунд замінюються до 30 задач, по одному новому виконавцю на задачу. Попередній підбір проєкту до створення запуску залишається окремою операцією планування.

## Послідовність

1. Оркестратор чекає завершення всіх активних задач. Прийняті результати та файли залишаються на місці.
2. Відбирає невдалі задачі, які можна безпечно перепризначити, перевіряє кількість спроб, бюджет, актуальність плану й чистий стан Git workspace.
3. AI-керівник отримує початкові вимоги, діагностику збою та прийняті результати залежностей. Невдалі маршрути накопичуються у списку виключень.
4. Зберігаються вимоги до запису, інструментів, контексту й тарифу. Безкоштовна задача не переводиться на підписку. Нові тарифи чи невідомі маршрути не дозволяються.
5. Після відповіді повторно перевіряються доступні кандидати, бюджет і незмінність прийнятого Git commit та плану.
6. Старі outputs, помилка й candidate workspace переходять у `task.history`. Нова спроба отримує інший worktree від прийнятих файлів. Виконавцю передаються діагностика та причина заміни.
7. Повторно відкриваються лише потрібні заблоковані залежні задачі та батьки. Успішні, скасовані та заблоковані через скасування задачі не перезапускаються.

Конфлікт інтеграції (`WORKSPACE_CONFLICT`) не запускає перепризначення моделі. Локальний UI-сервер дозволяє одну спробу узгодження тим самим виконавцем у новій worktree з повторними перевірками та в межах спільного бюджету. Повторний конфлікт, недоступні обов'язкові перевірки (`CHECKS_BLOCKED`), незбережені сторонні зміни у прийнятій папці та вичерпаний бюджет зупиняють автоматичне відновлення. Збій окремого `reviewerId` також потребує втручання; самостійна задача перевірки може перепризначатися як звичайна задача. Відновлення через зміну моделі не виправляє несправний sandbox.

## API і події для UI

`POST /api/execution/runs/:id/recover` з JSON `{}` запускає ручне відновлення невдалого завершеного запуску. Для core API адреса `/runs/:id/recover`. Діють звичайні локальні auth та same-origin перевірки. Паралельний запуск того самого проєкту, зміна плану, завершений/скасований запуск, повторний активний запит або вичерпаний ліміт відхиляються. Ручний запит не збільшує бюджет чи кількість дозволених спроб. За вимкненого автоматичного режиму один ручний запит запускає один раунд.

Основний стан запуску залишається `running` або `paused` під час підбору; остаточний `failed` надсилається лише після зупинки відновлення. `run.recovery` містить `status`, `reason`, `rounds`. У раунді зберігаються невдалі задачі, base commit, AI-пропозиція, причини замін, виключені маршрути та usage керівника.

`GET /api/execution/status` повідомляє підтримку в `capabilities.recovery`: `automatic`, `defaultAttempts`, `maxAttempts`. Автоматичний підбір починається, коли задачі досягли кінцевих станів; незавершене очікування approval лишається під контролем користувача.

SSE передає події `recovery.requested`, `recovery.started`, `recovery.manager_started`, `recovery.manager_completed`, `recovery.applied`, `recovery.completed`, `recovery.stopped`, `recovery.cancelled`. У них є зрозумілий `message`, що вже відображається звичайним журналом активності. `recovery.applied` також передає повний список задач і оновлений snapshot агентів; canvas не потребує перезавантаження сторінки. Скасування перериває виклик керівника; фінальний маніфест чекає завершення його процесу. Пауза зберігає отримане призначення, а нові виконавці чекають продовження.

Для окремого UI-блоку можна показати номер раунду, `round.manager.model`, `round.proposal.assignments[].reason`, `excludedRouteIds`, `task.history` та кнопку ручного відновлення. Первинний редагований план робочого простору не переписується.

## Продовження після таймауту

За замовчуванням виконання та AI-підбір заміни не мають фіксованого дедлайну. Скасування, бюджети викликів і перевірки тарифів залишаються активними. Необов’язкові `ORCHESTRATOR_EXECUTOR_TIMEOUT_MS` та `ORCHESTRATOR_RECOVERY_TIMEOUT_MS` задають явні ліміти; core-проєкти підтримують `limits.timeoutMs: null` або число мілісекунд. Час очікування слота виконавця не враховується у його ліміт.

Кнопка «Продовжити після таймауту» викликає `POST /api/execution/runs/:id/continue` для завершеного невдалого запуску. Повторюються лише задачі з таймаутом; залежності розблоковуються, готові задачі не повторюються. Спроба стартує з прийнятої папки в новій ізольованій worktree. Часткові неприйняті зміни попередньої спроби залишаються у старій worktree.

Продовження використовує поточний налаштований дедлайн, зокрема `null` замість старого зашитого ліміту. Воно зберігає ID запуску, готові результати, витрачені виклики, історію спроб та раундів. Загальний бюджет і ліміт AI-перепризначень не збільшуються. Це окрема ручна повторна спроба з тими самими виконавцями, без додаткового підбору керівником. Подія `run.continued` фіксує зміну ліміту та задачі. Зміна плану або прийнятої папки, активний паралельний запуск, відсутність таймауту чи бюджету блокують дію. Підписка та тариф повторно перевіряються перед модельними викликами.

## Уточнення вимог

Окрема кнопка «Повторити після перевірки доступу» використовує `POST /api/execution/runs/:id/retry-access` для задач із `MODEL_ACCESS_BLOCKED`. Перед зміною стану повторно перевіряються маршрути всіх призначених виконавців, незмінність плану й прийнятої папки та належність чернеток. Якщо доступ досі заборонений, запит відхиляється до нового модельного виклику. Після відновлення квоти зберігаються ті самі виконавці, робочі папки, уточнення користувача, готові результати, історія та облік викликів. Загальний бюджет і кількість автоматичних перепризначень не збільшуються; повторна перевірка політики при самому виклику залишається активною.

Повний набір після додавання повторної перевірки доступу: 207 успішних тестів. Сценарій покриває відмову без нового модельного виклику за недоступної квоти, продовження після відновлення доступу з тієї самої чернетки, перезапуск сервера, захист від паралельного повтору та змін плану, папки чи бюджету. У браузері перевірено кнопку повтору, перехід до `running` та SSE; за збереженими подіями підтверджено, що реальний виконавець отримав уточнення користувача. Це не підтверджує завершення всіх задач конкретного проєкту.

Після додавання цього сценарію пройшли 207 автоматичних тестів. Нові перевірки покривають відмову до модельного виклику за недоступної квоти, повтор після відновлення доступу й перезапуску сервера, збереження незавершеної worktree та готових задач, подвійний запит і відхилення змін плану, папки, бюджету, іншого типу помилки або активного паралельного запуску.

Після додавання цього продовження пройшли 207 автоматичних тестів. Зокрема перевірено відмову до нового виклику за недоступної квоти, продовження з тієї самої чернетки після відновлення доступу та перезапуску сервера, збереження готових задач і бюджету, а також відхилення зміненого плану, сторонніх змін у workspace, вичерпаного бюджету, іншого типу помилки та активного паралельного запуску.

`status: blocked` у звіті виконавця зберігається як `AGENT_BLOCKED`. Запуск переходить у `blocked`: це очікування уточнення або втручання, без автоматичного витрачання раундів на заміну моделі. Звіт, перевірки та ізольована папка залишаються чернеткою. Підготовлені файли не інтегруються й залежні задачі не позначаються завершеними. Повідомлення та кнопка «Уточнити вимоги» відображаються окремо від технічних помилок.

`POST /api/execution/runs/:id/clarify` приймає `taskId`, `answer` (до 6000 символів) та `scope: task|project`. Уточнення всього проєкту зберігається як `executionBrief` у запуску й UI-проєкті та передається подальшим виконавцям і керівнику recovery. Воно не означає автоматичного виконання критеріїв, прийняття чернетки чи дозволу на публікацію. Обов’язкові технічні перевірки залишаються обов’язковими.

Перед продовженням перевіряються актуальність плану та уточнень, залишок бюджету, відсутність інших активних запусків, чистота прийнятої папки, корінь, Git-репозиторій, гілка й базовий commit чернетки. Виконавець продовжує з тієї самої worktree; усі готові задачі зберігаються. Уточнення записується в історію та подію `run.clarified`. Підписка й тариф перевіряються повторно при виклику моделі. Старі збої виду `Codex blocked:` відновлюють structured report із збережених JSON-подій, якщо він доступний; це не приймає їхні файли як успішний результат.

Приклад уточнення: магазин має бути технічно готовий до майбутнього реального запуску, а продажі зараз вимкнені. Відсутні комерційні дані оформлюються як конфігурація, перевірки й checklist майбутнього запуску. Тестові дані позначаються явно; реальні залишки, ціни, погодження та зовнішні операції не вигадуються.

Після додавання уточнень пройшли 197 автоматичних тестів. Перевірено structured та старі заблоковані звіти, завершення SSE у стані `blocked`, збереження usage та чернетки, продовження з тієї самої папки після перезапуску сервера, передачу загального уточнення у виконання, відхилення зміненого плану, сторонньої папки, вичерпаного бюджету та порожньої відповіді. Це перевірка механізму оркестрації; готовність конкретного магазину визначають результати його власних задач і перевірок.

JSON-запити декодуються як UTF-8 лише після об’єднання мережевих байтів. Раніше межа HTTP-блоку могла пошкодити українську літеру у великому workspace PUT і спричинити справжню різницю fingerprint без редагування користувачем. Спільний parser використовується для планування, workspace, виконання та core API; некоректний UTF-8 відхиляється. Регресійні тести перевіряють усі межі байтів українського тексту й emoji, великі запити з блоками 64 KiB та обмеження розміру в байтах.

## Негативні перевірки готовності

Звіт Codex розрізняє `kind: assertion` та `kind: exit_code`. Для звичайної перевірки `expectedExitCode` й `actualExitCode` дорівнюють `null`, а її статус зберігається. Для перевірки коду завершення потрібні явні цілі невід’ємні значення обох кодів; сервер обчислює результат їх порівняння. Наприклад, вимкнений магазин без товарів має відхилити `--require-ready` кодом `1`: `expectedExitCode: 1`, `actualExitCode: 1` означає успішну перевірку захисту, а не готовність реальної комерції.

Розбіжність кодів залишається помилкою навіть при заявленому моделлю `status: passed`. `not_run` не перетворюється на успіх. Старі звіти без явного типу перевірки зберігають статус; тексту «очікувана відмова» недостатньо для автоматичного прийняття. Початковий статус порівняної перевірки зберігається в `reportedStatus`. Інструкція нового контракту передається також замороженим виконавцям попередніх запусків.

Відхилений `completed`-звіт із реально незадоволеною обов’язковою перевіркою зберігається в чернетці. Його можна уточнити через той самий `/clarify`; це запускає нову перевірку виконавцем зі збережених файлів, а не приймає результат примусово. Звичайне автоматичне відновлення технічних збоїв залишається під контролем попередніх лімітів і бюджету.

Конфлікт інтеграції перевіреного результату також можна продовжити через `/clarify`. Оркестратор перевіряє збережений commit, гілку, спільний репозиторій та чистоту прийнятої папки, створює окрему worktree від актуального прийнятого результату й об’єднує в ній чернетку. Виконавець отримує перелік конфліктів, узгоджує зміст і повторює перевірки. Прийняті файли та початкова чернетка залишаються недоторканими до успішної інтеграції; повторний виклик входить до спільного бюджету. Старі конфлікти без записаного commit підтримуються лише для одного підтвердженого commit оркестратора безпосередньо над збереженою основою.

## Продовження після скасування

Кнопка «Продовжити після скасування» надсилає `POST /api/execution/runs/:id/resume-cancelled`. Сервер перевіряє ревізію плану, прийняту Git-папку, збережені чернетки, відсутність активного запуску цього проєкту і доступ до призначених моделей. Якщо перевірки успішні, сервер продовжує той самий запуск і повертає в чергу задачі, зупинені разом із ним. Завершені й окремо скасовані задачі зберігають статус. Збережені worktree використовуються повторно, а кожен новий виклик враховується в початковому бюджеті. Підтримуються попередні записи скасування. Після перезапуску для повторного використання чернеток потрібне підтвердження, що старий виконавець завершився.

## Локальний верифікатор

Локальний верифікатор приймає чернетку після успішних обов’язкових тестів із політики проєкту в `.orchestrator/ui/host-verification.json`. Точні записи команд мають пріоритет. Для довірених проєктів оператор може увімкнути `nodeProjectChecks.http: true` і задати абсолютний шлях `nodeProjectChecks.postgresBin`. Це дозволяє підхоплювати нові перевірки з `package.json` чернетки. HTTP-скрипт має містити `node --test` і явний список файлів `tests/integration/*.test.mjs`. PostgreSQL-скрипт `test:<назва>-postgres` має запускати відповідний `scripts/test-<назва>-postgres.mjs`. Верифікатор викликає Node.js напряму з обмеженим середовищем. Ці правила дозволяють виконання коду проєкту на локальній машині й задаються за межами робочих папок агентів.

З параметром `automatic: true` оркестратор запускає дозволені перевірки зі збереженої чернетки навіть тоді, коли інші обов’язкові перевірки ще недоступні. Він прив’язує локальні результати до перевіреного дерева файлів. За незмінного дерева успішні локальні перевірки зберігаються для наступної спроби. Чернетку приймають і продовжують залежні задачі після виконання всіх обов’язкових перевірок.

У `taskPreflights` оператор може додати попередню перевірку для конкретної задачі. Поле `before` має збігатися з назвою обов’язкової перевірки у звіті. Верифікатор зберігає код завершення і останній рядок виводу попередньої перевірки. Її успіх підтверджує готовність до відповідного тесту, який має пройти окремо. Для виводу використовуйте лише діагностику, яку можна показувати в журналі.

Після погодження тестового обсягу оператор може задати `testCompletion` з полями `taskId`, `deferCheck`, `require` і `deferTasks`. Верифікатор перевіряє всі перелічені в `require` локальні сценарії. Він переносить до реального запуску лише явно названу перевірку зі статусом `not_run` і нерозпочаті залежні етапи зі списку `deferTasks`. У журналі зберігається підсумок тестового запуску, у плані ці етапи мають статус «Відкладено до запуску».

З тими самими налаштуваннями верифікатор підтримує прямі команди Node.js. Для `node --test` потрібен щонайменше один файл із `tests/integration/`. У тому самому виклику можуть бути модульні тести з `tests/`. Для PostgreSQL підтримується `node scripts/test-<назва>-postgres.mjs`. Параметр `nodeProjectChecks.browser: true` дозволяє `node scripts/check-<назва>-browser.mjs` або npm-скрипт `test:<назва>-browser`, що запускає той самий файл. Правила приймають явні відносні шляхи без додаткових прапорців.

Дерево файлів, яке пройшло тести в тимчасовому Git worktree, має збігатися з деревом чернетки перед інтеграцією. Приймання не витрачає виклик моделі, а залежні задачі продовжують той самий запуск.

Файл створює оператор один раз для перевірених команд конкретного проєкту. Ідентифікатор проєкту є в експорті робочого простору. Код перевірок виконується з правами локального сервера, тому вмикайте цей режим для проєктів і команд, яким довіряєте. За `"automatic": true` перевірка запускається після розпізнаного блокера середовища. За `false` достатньо натиснути «Перевірити локально й продовжити». Цей шлях доступний для задачі з одним виконавцем, яка не потребує окремого рецензента або об’єднання підзадач. Якщо перевірка падає, чернетка залишається заблокованою, а причина потрапляє в журнал.

```json
{
  "projects": {
    "project-id": {
      "automatic": true,
      "checks": {
        "npm run test:http": {
          "argv": ["--test", "test/http.test.js"],
          "timeoutMs": 120000,
          "expectedExitCode": 0
        }
      }
    }
  }
}
```

Автоматична черга переходить до інших сумісних чернеток після невдалої перевірки. Для одного звіту є одна автоматична спроба. Параметр `retryTransientBrowser: true` дозволяє ще один запуск конкретного браузерного тесту, якщо він завершився таймаутом очікування UI або взагалі не створив звіту.

## Перевірка

У майстрі запуску рекомендований бюджет враховує кількість виконавців у плані та запас на повтори. Для зупиненого запуску кнопка «Збільшити бюджет» оновлює ліміт цього запуску й додає запис у журнал. Задачі, які вичерпали бюджет, можна окремо продовжити з чернеток. Зміна ліміту сама не викликає моделей.

Якщо всі незавершені обов’язкові перевірки мають ознаки недоступного середовища, панель показує їхні команди й причини. Автоматичне перепризначення таких задач не запускається. Дія «Повторити перевірки» передає виконавцю інформацію про виправлені передумови або результати локальної перевірки, з якими він продовжує зі збереженої чернетки.

17 інтеграційних тестів покривають успішне відновлення, дві послідовні заміни, спроби й бюджети, некоректні AI-відповіді, SSE, ручний запит, паузу, скасування, зміну плану й файлів, дочірні та скасовані задачі. Окремо перевірено повний HTTP-шлях від AI-призначення до відновлення з явно вибраним керівником, пріоритет налаштування проєкту та зупинку без підміни, якщо вибраний керівник став недоступним. Тести використовують контрольовані відповіді провайдерів і не викликають реальні AI-моделі.

Окрема жива перевірка від 15.11.2026 ввела один контрольований збій у першу спробу реалізації, після успішного створення README. GPT-6.1 Sol за підпискою сам обрав новий безкоштовний маршрут GLM 5.3 Flash Free. Новий виконавець створив утиліту `safeDivide` і тести; DeepSeek V4.1 Flash Free виконав read-only перевірку. Усі 12 Node-тестів пройшли в sandbox. README зберігся без змін, невдалий `partial.txt` не потрапив у прийняту папку. Один запуск завершився після одного раунду відновлення за 5 викликів із ліміту 10; готова задача документації не повторювалася.

Це перевірка механізму з контрольовано введеним збоєм та реальними подальшими модельними викликами. Сирі події, usage і локальні шляхи збережені приватно в `.orchestrator/`.

Після виправлення таймаутів пройшли 188 автоматичних тестів. Додано перевірки явного дедлайну та очікування слота, налаштувань UI-сервера, продовження після вичерпання AI-перепризначень і перезапуску сервера, сумісності зі старим числовим кодом таймауту, збереження готових файлів та історії. Зміна плану, прийнятої папки, вичерпаний бюджет, інший тип помилки та активний паралельний запуск відхиляють продовження. Модельні відповіді в цих тестах контрольовані; повний користувацький проєкт автоматично не запускається.
