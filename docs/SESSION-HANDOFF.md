# Orcestrator — контекст для нового чату / сеансу

Оновлено: **18.11.2026**, часовий пояс Europe/Kiev. Це передача контексту локального проєкту, а не підтвердження готовності всього продукту. Стан запусків і квот потрібно перевіряти заново.

## 1. Що будуємо

**Orcestrator — локальний оркестратор AI-моделей та агентів.** Користувач описує задум або готовий проєкт, система допомагає сформувати концепцію, складає детальний план і підбирає доступні моделі під конкретні задачі. Сильна модель керує плануванням і розподілом роботи, виконавці реалізують задачі; мета — якість із раціональним використанням токенів.

Потрібні одночасно API-адаптери та встановлені CLI-агенти, кілька агентів на одну задачу, незалежні паралельні задачі, pipeline, рецензування, субагенти, залежності, керування виконанням, журнали та перевірені результати. Частина розширеного цільового дизайну ще не реалізована.

**Не плутати два проєкти:** основна розробка тут — оркестратор. Локальний інтернет-магазин телефонів — його перевірочний проєкт, який виконують агенти в окремій керованій папці.

## 2. Вимоги та домовленості користувача

- Спілкуватися українською. Виконувати доручену роботу без зайвих повторних підтверджень; повідомляти про реальні зміни й блокери.
- Дозволені справді безкоштовні маршрути та включений доступ уже наявних підтверджених підписок. **Оплата за фактично використані токени / запити — платний маршрут і виключена.** Не підключати API billing чи додаткові кредити як обхід.
- Codex має використовувати штатний вхід ChatGPT. Користувач підтвердив, що Automatic reload вимкнено / не вмикав. Підписка Gemini / Antigravity також була підключена; доступність завжди перевіряти через каталог.
- Під час останньої зупинки через квоту користувач **обрав чекати Codex**, а не перемикатися на Gemini. Не вважати стару квоту або час її відновлення актуальними сьогодні.
- Концепцію можна пропустити, якщо ідея вже продумана. Модель для концепції та планування підбирається автоматично відповідно до опису проєкту.
- Команду має підбирати AI під задачі плану. Використовувати реальний каталог, не вигадувати model ID, підписки, можливості або рейтинги якості.
- Одна картка на модель і провайдера; рівень роздумів обирається при додаванні в команду, а не окремими дубльованими картками.
- UI — космічна стилістика й інтерактивна сонячна система. Показувати конкретну модель, а не лише назву конектора на кшталт «Codex CLI». Камера має підтримувати обраний об’єкт.
- Частину UI користувач доручав Hydrogen / Antigravity. У робочій копії можуть бути їхні зміни: не перезаписувати чужу роботу й не скидати Git без перевірки.
- Для перевірочного магазину потрібна технічно завершена реалізація, готова до майбутнього запуску, **без фактичної публікації, продажів, замовлень і платежів**: товарів поки немає. Реальний каталог порожній. Комерційні налаштування й погодження — checklist перед активацією; не вигадувати їх і не блокувати через них незалежні технічні задачі. Реальні сесії з покупцями не проведені; не видавати їх за виконані.

## 3. Фактична реалізація та структура

Робочий корінь: `E:\orcestrator`. Windows / PowerShell, JavaScript ESM, Node.js 22+; у попередніх перевірках використовувався Node.js 24.13.0. У кореневого пакета немає зовнішніх npm-залежностей.

Стан зараз зберігається у **JSON**, а не SQLite. Вебпанель — HTML/CSS/JavaScript, сонячна система — власний WebGL-рендерер. Не описувати цільову багатопакетну архітектуру як уже реалізовану.

| Шлях | Призначення |
| --- | --- |
| `src/domain.js` | Проєкти, задачі, агенти, залежності, валідація й ліміти |
| `src/engine.js` | Планування виконання DAG, команди, делегування, review, пауза, скасування, продовження та інтеграція |
| `src/providers.js` | Адаптери провайдерів, CLI-процеси, звіти, usage, помилки та завершення процесів |
| `src/workspaces.js` | Ізольовані Git worktree, перевірка чернеток, інтеграція та конфлікти |
| `src/store.js` | Атомарне збереження JSON і повтори при тимчасових блокуваннях Windows |
| `src/execution-report.js` | Контракт перевірок, очікувані exit code, право виправлення відхиленого звіту |
| `src/http-body.js` | Читання JSON HTTP-запитів із коректним UTF-8 і лімітом байтів |
| `scripts/ui-server.js` | Локальна панель на `127.0.0.1:4311` |
| `scripts/execution-service.js` | API виконання панелі, перевірка ревізій, доступу та керованих папок |
| `scripts/model-registry.js`, `src/model-policy.js`, `scripts/subscription-guard.js` | Discovery моделей, політика тарифів і контроль квоти підписки |
| `scripts/planning-service.js`, `scripts/director-service.js`, `scripts/planner-selection.js` | Концепція, план, підбір керівника й точних моделей виконавців |
| `scripts/recovery-service.js` | Відновлення після збоїв без повторення вже прийнятих задач |
| `scripts/antigravity-service.js`, `scripts/opencode-service.js`, `scripts/file-worker.js` | Antigravity / Gemini, OpenCode та контрольовані файлові зміни |

| `test/` | Тести оркестратора; не плутати з `tests/` усередині згенерованого магазину |

Сценарій майстра: **задум → концепція або пропуск → план → AI-підбір команди → створення проєкту → окремий запуск виконання**. Пропозиція AI-команди, профілі ролей і фактичні виконавці запуску — різні сутності.

Реалізовані контрольовані маршрути Codex, OpenCode і Antigravity. Наявність низькорівневого адаптера API / CLI не означає, що політика дозволяє його запуск або підтверджує безкоштовність.

## 4. Останні суттєві зміни

### Планування, каталог та UI

- Автовибір керівника за проєктом; збереження концепції, плану та призначень із захистом від застарілих ревізій.
- Групування моделей і вибір рівня роздумів при додаванні. Коректніше відображення реальних моделей у бібліотеці та сонячній системі.
- Покращення розмірів полів концепції / плану, збереження чернетки майстра й зрозуміліші помилки.
- Валідація дозволених маршрутів AI-підбору команди та structured-output схем.
- SSE й точкове оновлення DOM, щоб потік подій не перебудовував 3D-сцену повністю.

### Надійність виконання

- Для реальних виконавців і керівника відновлення загальний timeout за замовчуванням `null`. Явний дедлайн можна задати через `ORCHESTRATOR_EXECUTOR_TIMEOUT_MS` / `ORCHESTRATOR_RECOVERY_TIMEOUT_MS`; скасування, квоти та бюджети збережені. Планування має окремі налаштування — не поширювати це твердження на кожен запит.
- `/continue` продовжує відповідні задачі після timeout, `/retry-access` перевіряє доступ заново й продовжує збережену чернетку. Підтримані terminal-стани `failed` та, для доступу, `blocked`; історія, готові результати й витрачені виклики не скидаються.
- `/clarify` передає уточнення разом із чернеткою й запускає перевірку знову. Це не примусове прийняття результату. Уточнення можуть поширюватися на весь проєкт через `executionBrief`.
- `AGENT_BLOCKED` відрізняється від технічної помилки й не спричиняє марних перепризначень моделі.
- Усунуто пошкодження українського UTF-8 при розбитті великих HTTP-запитів на чанки; воно раніше помилково викликало повідомлення про зміну плану.
- Коди й діагностика помилок CLI зберігаються зі звітом та usage; повідомлення не повинні розкривати секрети.

### Перевірки, Git та Windows

- Перевірка має `kind: exit_code` з явними `expectedExitCode` / `actualExitCode` або `kind: assertion` з обома кодами `null`.
- Очікуваний exit 1 у тесті забороненого production-запуску є успішною перевіркою, якщо це явно зазначено. `not_run` і справжній провал обов’язкової перевірки не перетворюються на успіх.
- Для Git-конфліктів створюється нова worktree від актуального прийнятого результату, куди об’єднується попередня чернетка. Початковий результат зберігається; агент узгоджує файли та повторює перевірки.
- Git-перевірка після merge відхиляє незавершені маркери конфлікту, але більше не зупиняє інтеграцію через звичайні пробіли або порожній рядок наприкінці документа.
- **UI-сервіс увімкнув одну автоматичну спробу узгодження інтеграції тим самим виконавцем.** Вона працює для одного виконавця на задачу, враховує reviewer і спільний бюджет. Повторний конфлікт або недостатній бюджет зупиняють її; нескінченного повтору немає. Звичайний `Engine` без цієї опції автоматичне узгодження не вмикає.
- Подія `workspace.resolving` пояснює узгодження в журналі. Попередні результати зберігаються в історії. Під час узгодження делегування вимкнене.
- Атомарний запис `state.json` повторює rename до 8 спроб для `EPERM` / `EACCES` / `EBUSY` із короткою обмеженою затримкою. Інші помилки не приховуються. Це усуває тимчасове Windows-блокування, яке раніше переривало перевірку підписки.

## 7. Як безпечно почати наступний сеанс

1. Прочитати цей файл і перевірити `git status --short`. За потреби звіритися з наявними `AGENTS.md`, не перезаписуючи сторонні зміни.
2. Перевірити, чи відповідає UI API. Якщо сервер працює, читати стан через нього. Якщо не працює — читати JSON звичайним `fs.readFile` / `Get-Content`, **не створювати `new Store()` для перегляду живого сховища**: конструктор позначає активні запуски як `interrupted` і записує стан.
3. Визначити актуальний запуск і його задачі. Не використовувати старий PID, час скидання квоти, скриншот або історичний JSON як дозвіл на новий виклик.
4. Якщо доручено продовжити виконання: запустити UI-сервер лише за відсутності іншого екземпляра, оновити каталог / перевірку підписки та продовжувати **той самий** запуск через штатні API. Для збережених T09/T10 перевірити придатність `/retry-access` після свіжого підтвердження квоти.
5. Не скидати completed-задачі, бюджет викликів, історію чи вже підготовлені чернетки. Не змінювати закріпленого керівника й вибір Codex без підстав у новому дорученні користувача.
6. Відрізняти справжню технічну помилку, очікувану захисну відмову, нестачу доступу, Git-конфлікт і невиконані передстартові комерційні погодження.
7. Після зміни коду виконати доречні перевірки; після їх успіху не повторювати їх без нової причини. Для простих правок документації достатньо перевірити зміст і посилання.

Локальні службові матеріали: `.orchestrator/ui/state.json`, `.orchestrator/workspaces/`, `.orchestrator/workspaces/.runs/`, `.orchestrator/quota-wait-handoff.json`, `.orchestrator/continue-shop-stage.mjs`. Вони виключені з Git; старі helper-команди та історичні записи не виконувати навмання.

### Основні команди

```powershell
Set-Location E:\orcestrator
git status --short
npm run ui       # лише якщо іншого UI-сервера немає
npm run check
npm test
```

UI: `http://127.0.0.1:4311`. Низькорівневий core API використовує окремий сервер / порт 4310; не плутати його API з API панелі.

Для локального API панелі службовий токен отримується з `GET /api/execution/status`, передається в `X-Execution-Token` і не виводиться у відповідь користувачу чи документацію. Не читати секрети з `.env.local` для звичайної перевірки стану.
