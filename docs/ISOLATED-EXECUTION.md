# Ізольоване виконання та потік подій

## Від AI-призначення до запуску

У вкладці «Команда» AI-директор підбирає точні `routeIds` із серверного каталогу. Керованому OpenCode-виконавцю потрібен `workspaceWrite`, але не прямі інструменти моделі: файли застосовує сервер. Типове обмеження — одна модель на задачу; за потреби можна дозволити до шести.

Діалог запуску показує актуальну збережену пропозицію. `POST /api/execution/runs` приймає `{projectId, revision, proposalId}`. Сервер перевіряє ID, ревізію, fingerprint плану та доступність маршрутів, компілює фактичних виконавців і фіксує їх у snapshot запуску. Клієнтські назви моделей та підроблені тарифи не є дозволом. Без пропозиції залишається ручне призначення доступних моделей ролям. Кожен модельний виклик повторно перевіряє каталог; платного fallback немає.

## Файлові виконавці

OpenCode отримує обмежений текстовий контекст із керованої папки та повертає JSON-зміни. Сервер перевіряє відносні шляхи, SHA-256 попереднього вмісту, розміри, дублікати, секретні й службові файли та symlink до застосування пакета. Модель не має shell, MCP або доступу до файлової системи. Для паралельних виконавців створюються окремі anonymous runtime homes.

Для змін JS/TS потрібні Node-тести. Сервер сам запускає їх через native `codex sandbox`; це механічний запуск команди, без AI-запиту та без кредитів Codex. Потрібен сумісний Codex CLI і Node з permission model (перевірено з Node 24.13). `ORCHESTRATOR_SANDBOX_COMMAND` дозволяє задати абсолютний шлях до CLI; далі використовуються executor/planner command або `codex` у PATH.

Профіль sandbox забороняє мережу та доступ поза необхідними runtime-шляхами й worktree. Додатково Node отримує файловий доступ лише до worktree, без дозволів на дочірні процеси й native addons. Read-only перевірка не отримує запису. Windows запуск використовує `--preserve-symlinks` для уникнення realpath-звернень до заборонених предків; перед цим сервер відхиляє symlink у папці. Недоступний sandbox або непроведена обов'язкова перевірка блокує задачу; запуск без sandbox не підставляється.

Наразі автоматичний runner підтримує Node-тести, без довільних shell-команд, встановлення залежностей чи runner для інших мов. Успіх тестів є перевіркою конкретних сценаріїв; відповідність усім вимогам потребує належних тестів та огляду.

## Паралельність і прийняття змін

UI створює керований Git-репозиторій проєкту. Кожна задача отримує окремий worktree; паралельні агенти однієї задачі — додаткові worktree від спільного base commit. Pipeline працює послідовно в папці задачі. CLI-lock прив'язаний до фізичної папки, тому незалежні worktree виконуються одночасно в межах `concurrency`.

Після перевірок і заданого review сервер комітить результат, виконує `merge-tree` відносно актуальної прийнятої версії та лише після успішного злиття просуває її через fast-forward. Залежна задача стартує після інтеграції залежностей. Конфлікт або сторонні незбережені зміни блокують прийняття без автоматичного повтору чи перезапису. Звіти файлів враховуються навіть за згенерованого `.gitignore`.

Скасування не приймає незавершений candidate. Уже інтегровані результати інших задач залишаються. Worktree, гілки та конфліктні результати зберігаються приватно в `.orchestrator/workspaces/.runs/`; автоматичне очищення історії ще не реалізовано. Worktree організовує файлову паралельність; обмеження виконання коду забезпечує окремий sandbox.

## Керовані субагенти

У налаштуваннях проєкту доступні перемикач делегування, максимальна глибина (типово 2), ліміт усіх задач (типово 100), викликів і паралельності. Делегувати може одиночний виконавець у межах глибини, до десяти дочірніх задач за запит. `status: delegated` не можна поєднувати зі змінами файлів. Увесь пакет дочірніх задач перевіряється до зміни стану.

Діти мають окремі worktree та використовують тільки агентів snapshot запуску. Після їх завершення батько отримує інтегровані результати й виконує синтез без повторного делегування. У дереві UI видно вкладені задачі; можна скасувати задачу разом із нащадками. Це обмежене делегування, а не необмежене породження процесів.

## SSE

`GET /api/execution/runs/:id/events` передає `text/event-stream` після звичайної same-origin та `X-Execution-Token` перевірки. Токен передається заголовком. Для core API використовуйте `/runs/:id/events`, `Authorization: Bearer …` і `Accept: text/event-stream`.

- `snapshot`: повний узгоджений запуск і `cursor`.
- `change`: подія, метадані запуску й змінена задача; делегування містить повний список задач.
- `replay`: історичні події після `Last-Event-ID` або `?after=N`. Snapshot уже включає їх у стан.
- `finished`: повний фінальний запуск, включно з маніфестом UI після завершення активних процесів; потік закривається.

Події мають послідовні числові IDs; heartbeat надходить раз на 15 секунд. Повільний клієнт із переповненим буфером відключається. UI відновлює з'єднання з курсором, відкидає дублікати та оновлює DOM без повної заміни `#app` на подіях виконання. Canvas, камера, вибір сцени та поля вводу зберігаються. Повторного опитування активного запуску раз на 1,5 секунди немає.

## Перевірка

15.11.2026 реальний контрольний проєкт пройшов весь цикл: Big Pickle обрав DeepSeek V4.1 Flash Free для коду, Big Pickle для документації та Iceman Free для незалежної read-only перевірки. Перші дві задачі працювали паралельно; перевірка отримала інтегровані файли. Створено clamp utility, документацію й тести; 12 Node-тестів успішно виконано у sandbox. Кожен виклик повернув `cost: 0`. Це факт конкретного запуску, без гарантії майбутньої доступності безкоштовних квот.

Codex inference має окремий режим контрольованої підписки: квота, відсутність додаткових кредитів і підтверджений вимкнений Automatic reload. Це не атомарна серверна гарантія лише включеної квоти. Незалежний запуск `codex sandbox` не виконує inference. [Офіційні профілі дозволів](https://learn.chatgpt.com/docs/permissions).
