# Orcestrator

Локальне ядро оркестрації AI-команд: агенти через API та встановлені CLI, задачі з залежностями, паралельне виконання й кероване делегування.

Це робоча початкова версія сервісу та окремий інтерактивний UI-прототип. Node.js 22+; зовнішніх npm-залежностей немає.

## Панель керування

```powershell
cd orcestrator
npm run ui
```

Відкрийте [локальну панель](http://127.0.0.1:4311). `UI_PORT` дозволяє змінити порт.

Оформлення — космічний центр керування: темне зоряне тло, орбітальна ілюстрація, фіолетові й бірюзові акценти. Тема охоплює граф, картки агентів, форми та діалоги; її стилі розміщені в `apps/web/src/cosmic.css`. Ілюстрації — локальні SVG, без зовнішніх сервісів або завантажень.

У панелі працюють огляд простору, майстер задуму/концепції/плану/команди, бібліотека профілів, редагування задач та залежностей, призначення кількох агентів, граф/список/дерево субагентів, симуляція запуску з паузою і скасуванням, журнал, результати та експорт JSON/Markdown. Готовий задум дозволяє пропустити концепцію. AI-планування і підбір моделей доступні після конфігурації сервера; окремий явний демо-режим використовує шаблон і правила. [Підключення планувальника та семантика майстра](docs/AI-PLANNING.md). Дані зберігаються в localStorage цього браузера; після перезавантаження активна демонстрація відкривається на паузі.

Виконання задач у UI працює на демонстраційних даних: назви моделей у каталозі позначають профілі з неперевіреною доступністю. HTTP API ядра, реальне виконання задач через CLI/API, грошові ліміти та повна історія окремих запусків ще не підключені до панелі. Планувальник має власний локальний серверний endpoint з налаштованою через середовище авторизацією. Повторне демо замінює поточні демонстраційні результати проєкту. Секрети у UI не запитуються. Для зміни команди або плану завершіть/скасуйте активне демо. Симуляція враховує тільки кількість паралельних задач.

Поточна панель написана стандартними HTML/CSS/JavaScript modules без build-кроку як клікабельний прототип. Цільова реалізація на TypeScript та React визначена архітектурою. UI-файли розміщені в `apps/web/`, локальний сервер — `scripts/ui-server.js`. Backend-прототип у `src/` запускається окремо.

Подальша реалізація починається з [архітектури та структури проєкту](docs/architecture/README.md): модулі, дані, життєвий цикл задач, контракти, інтерфейс і план переходу від прототипу. Ці документи описують цільову систему; інструкції нижче стосуються наявного прототипу.

## Запуск

```powershell
cd orcestrator
npm test
npm run demo
npm start
```

Демо працює без ключів та модельних запитів, повертає явно позначені демонстраційні відповіді. Сервер слухає лише `127.0.0.1:4310` та друкує випадковий Bearer-токен доступу. Його потрібно передавати у всіх запитах. Можна задати `ORCHESTRATOR_TOKEN`, `PORT`, `ORCHESTRATOR_DATA` через середовище. `.env` автоматично не завантажується.

Окремий запуск JSON-проєкту:

```powershell
node src/cli.js run examples/demo.json
```

Не запускайте кілька процесів з одним `ORCHESTRATOR_DATA`: поточне JSON-сховище має одного власника. Не запускайте `demo` одночасно із сервером у тому самому сховищі. Для незалежного запуску задайте інший каталог даних.

## Що вже працює

- Створення та редагування проєктів з перевіркою номера ревізії. Запуск зберігає незмінний знімок конфігурації.
- Профілі агентів: роль, навички, інструкції, провайдер, модель, права доступу, увімкнення/вимкнення.
- Ручне призначення агентів або автоматичний підбір за кількістю збігів навичок. Це прозоре правило, а не виміряний рейтинг якості моделей.
- Кілька агентів на одну задачу: незалежні паралельні відповіді або послідовне передавання результатів (`pipeline`). Паралельні відповіді зберігаються окремо; автоматичного голосування поки немає.
- Одночасні незалежні задачі, залежності між ними, блокування наступних задач після помилки, виявлення циклів.
- Агент-рецензент: структуроване схвалення/відхилення, повторна спроба з передаванням зауважень.
- Делегування підзадач, дерево батьків/дітей, обмеження глибини, підсумкова відповідь батьківського агента після завершення дітей.
- Пауза/продовження запуску; скасування запуску або окремої задачі з дочірніми задачами; ручний дозвіл перед виконанням вибраних задач.
- Ліміти одночасних викликів, загальної кількості викликів, кількості задач, глибини делегування та часу виклику.
- Журнал подій, виходи агентів та usage, якщо провайдер повертає його; збереження стану на диск.
- При перезапуску незавершені запуски стають `interrupted`, без автоматичного повтору дій, які могли вже змінити файли.

## API керування

У другому PowerShell-вікні після `npm start`:

```powershell
$token = Read-Host 'Bearer-токен з вікна сервера'
$headers = @{ Authorization = "Bearer $token" }
$projectJson = Get-Content -Raw -Encoding UTF8 examples/demo.json
$project = Invoke-RestMethod http://127.0.0.1:4310/projects -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($projectJson))
$run = Invoke-RestMethod "http://127.0.0.1:4310/projects/$($project.id)/runs" -Method Post -Headers $headers
Invoke-RestMethod "http://127.0.0.1:4310/runs/$($run.id)" -Headers $headers
```

| Метод | Шлях | Дія |
| --- | --- | --- |
| GET | `/health` | Стан сервера |
| GET / POST | `/projects` | Список / створення |
| GET / PUT | `/projects/:id` | Читання / редагування; PUT вимагає поточну `revision` |
| POST | `/projects/:id/runs` | Новий запуск поточної ревізії |
| GET | `/runs` | Короткий список запусків |
| GET | `/runs/:id` | Задачі, дерево делегування, виходи та стан |
| GET | `/runs/:id/events` | Журнал подій |
| POST | `/runs/:id/pause` | Пауза перед наступними викликами; поточні завершуються |
| POST | `/runs/:id/resume` | Продовження паузи |
| POST | `/runs/:id/cancel` | Скасування запуску |
| POST | `/runs/:id/cancel-task/:taskId` | Скасування задачі та її нащадків |
| POST | `/runs/:id/approve/:taskId` | Дозвіл задачі з `requiresApproval: true` |

API призначений для довіреного локального оператора. Довільний CLI-профіль дозволяє виконувати програми з правами процесу сервера. Токен не є моделлю прав доступу для багатьох користувачів. Запити з браузерним `Origin` заблоковано; CORS та вебклієнта ще немає.

## Підключення моделей і CLI

Приклад змішаної команди: `examples/hybrid.json`. Перед запуском замініть `REPLACE_WITH_AVAILABLE_MODEL` на модель, доступну вашому API-акаунту, а `workspace` — на каталог потрібного репозиторію. Для Ollama задайте встановлену модель та `enabled: true`.

| `provider` | Налаштування | Поведінка |
| --- | --- | --- |
| `responses` | `baseUrl`, `model`, `apiKeyEnv` | HTTP Responses API, текстовий ввід/вивід |
| `chat` | `baseUrl`, `model`, необов'язковий `apiKeyEnv` | OpenAI-сумісний Chat Completions, зокрема локальний Ollama |
| `codex` | необов'язкові `command`, `model`, `access` | `codex exec --json`, prompt через stdin |
| `claude` | необов'язкові `command`, `model`, `access` | `claude -p --output-format json`, обмежений перелік інструментів |
| `cli` | `command`, `args` | Довільний процес; stdin → prompt, stdout → відповідь, ненульовий exit code → помилка |
| `demo` | без ключів | Демонстраційна відповідь, без реальної моделі |

Для API ключ береться зі змінної середовища, назва якої записана у `apiKeyEnv`; значення ключа не потрібно записувати у JSON. CLI використовують власну попередньо налаштовану авторизацію. API-агенти цієї версії генерують текст і не мають інструментів редагування файлів; для змін репозиторію потрібен CLI-агент.

На Windows запускаються native `.exe` або `node.exe` зі шляхом до CLI-скрипта. `.cmd`/`.bat` обгортки не запускаються через shell. У `command` можна вказати абсолютний шлях до executable. Для довільного CLI аргументи передаються масивом без shell-інтерполяції. Його фактичні права контролює оператор, а поле `access` не створює ОС-пісочницю.

Для Codex `access` за замовчуванням `read-only`; для редагування задайте `workspace-write`. Claude отримує інструменти читання або читання/редагування відповідно; це обмеження інструментів, а не ізоляція операційної системи. Автоматичного обходу sandbox/permissions немає. Паралельні CLI-запуски в одному фізичному каталозі серіалізуються, включно з читачами. Ізольовані worktree для паралельних редакторів ще не реалізовані.

Документація інтеграцій: [Codex non-interactive](https://developers.openai.com/codex/noninteractive), [OpenAI text generation](https://developers.openai.com/api/docs/guides/text), [Claude programmatic mode](https://code.claude.com/docs/en/headless), [Ollama API compatibility](https://docs.ollama.com/api/openai-compatibility).

## Делегування і перевірка

Для задачі з одним агентом встановіть `allowDelegation: true`. Агент може повернути:

```json
{"subtasks":[{"title":"Перевірити API","prompt":"Перевір контракт і граничні випадки","skills":["testing"]}]}
```

Диспетчер перевірить весь список, призначить агентів з реєстру проєкту й створить дочірні задачі. Батьківський агент отримає їхні результати для узагальнення. Дозволено до 10 дітей за одну відповідь; загальні межі задаються в `limits`. Нові довільні executable з відповідей моделей не створюються.

`reviewerId` задає агента, який має повернути `{"approved":true,"feedback":"..."}`. Невалідна відповідь або відхилення завершує спробу помилкою. Поле `retries` дозволяє повтори; за замовчуванням їх немає, бо повтор CLI-задачі може повторити файлові зміни. `requiresApproval` перевіряється перед першим викликом задачі; це не інтерактивний дозвіл кожної внутрішньої дії CLI.

## Межі цієї версії

- `concurrency` і `maxCalls` діють на один запуск, а не на весь сервер. Кількість внутрішніх модельних викликів CLI ними не обмежується.
- `maxOutputTokens` передається HTTP API; для CLI немає універсального еквівалента. Грошового бюджету та розрахунку вартості поки немає.
- Обмеження часу передається HTTP-запитам і CLI-процесам. На Windows використовується `taskkill /T`; якщо ОС відмовляє, fallback зупиняє основний процес. Завершення відокремлених дочірніх процесів потребує окремого контролю ОС.
- Немає перемикання на іншого провайдера, потокової відповіді, embeddings/RAG, MCP, голосування та автоматичного злиття коду.
- Сховище — один JSON-файл, без транзакцій між процесами; для production потрібні база даних, диспетчер воркерів, ізоляція і спостережуваність.
- Справжні платні запити та модельні сесії CLI ще не перевірялися. HTTP-протоколи перевіряються локальними тестовими серверами, CLI — тестовими Node-процесами.
